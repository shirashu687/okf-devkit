# 引継ぎ・再開手順

この手順は、作業を中断したときに別セッションまたは別担当が同じ作業を再開できる最小状態を、検証結果と一緒に残すための手順である。作業を同じ文脈で続けられる場合、毎回のhandoff実行は必要ない。

## 1. 中断前に同じworklogを更新する

通常・大の作業では `harness/state/journal/<task-id-or-slug>.md` を使う。小作業でも、別セッションへ渡すなら [worklogテンプレート](../templates/worklog.md) を同じ場所へ複製する。新しい状態ファイルを別に作って、worklogと正本を分けない。

中断前に次を現物で確認してから記録する。

- 作業場所、ブランチ、開始SHA、最新HEAD。
- 開始時に存在した変更、今回の変更、未追跡ファイル。
- 依頼、対象外、完了条件への参照。
- 今回の判断と根拠への参照。既決事項をworklogへ複製しない。
- 実行済み検証の最新状態。結果は成功 / 失敗 / 未実行 / 実行不能の4値だけにする。
- 仕様軸・標準軸のreview結果、残作業、残存リスク。
- 妨げ、再開前提、具体的な次の一手、期待する結果。
- 更新日時と、必要なら証拠の保存先。

「次の一手」は「調べる」「続ける」ではなく、対象、操作、期待結果が分かる一件にする。秘密情報、会話全文、巨大な実行ログは記録しない。

## 2. 再開時に読む順序を固定する

再開するセッションは次の順に読む。

1. [AGENTS.md](../../../AGENTS.md) — 入口と優先順位。
2. [日本語作業ガイド](../guide.md) — 作業区分と読む条件。
3. [config.md](../../project/config.md) と [requirements.md](../policy/requirements.md) — 配置、コマンド、制約、実行前提。
4. `harness/state/journal/<task-id-or-slug>.md` — この作業の状態、最新検証、次の一手。
5. worklogから参照された仕様、チケット、決定、差分、証拠 — 必要なものだけ。

worklogに書かれた要約を、そのまま現物の代わりにしない。読了後、再開セッションで次を照合する。

- 現在の作業ディレクトリとブランチが記録どおりか。
- HEADと作業ツリーが記録された対象版どおりか。
- 開始時の既存変更、今回の変更、未追跡ファイルが区別できるか。
- 参照されたファイル、検証コマンド、証拠がまだ存在するか。
- 記録後に変更された対象がないか。

差異があれば、差異をworklogへ追記してから次の一手を見直す。対象が変わった後の検証を、前セッションの成功で代用しない。

## 3. 次の一手を実行する

照合が終わったら、worklogの具体的な次の一手を一件だけ実行し、結果を同じworklogへ追記する。実行前提が満たせない場合は、実行不能として理由、代替確認、限界、再実行条件を記録する。

検証を行った場合は [検証・完了報告手順](verify-report.md) の4値と再試行の規則に従う。作業が完了したら完了条件、検証、review、残存リスク、retro判定を更新する。未完了なら、次に再開する人が一回で実行できる次の一手を新しく残す。

## 4. 上流handoffとの接続

上流 `handoff` が一時文書を作る場合、その文書は入口、worklogの絶対パス、次セッションで行う用途への参照にとどめる。作業状態、検証結果、判断の正本はworklogに置き、一時文書へコピーしない。一時文書が消えてもworklogだけで再開できる状態を保つ。
