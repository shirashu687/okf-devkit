# 検証・完了報告手順

この手順は、対象プロジェクトの必須検証を選び、対象版を固定し、結果を正確に報告するための共通契約である。プロジェクト固有のコマンドや実行場所は書かず、[プロジェクト設定](../../project/config.md)の「検証の実行場所とコマンド」を参照する。

## 1. 適用範囲を決める

作業開始時に [日本語作業ガイド](../guide.md) で小・通常・大を選び、依頼、完了条件、対象外を確認する。

| 区分 | この手順で必ず行うこと | 追加の記録 |
| --- | --- | --- |
| 小 | 対象プロジェクトの既存テストを含む必要な検証を実行し、短い報告を作る | 計画書、grilling、worklogは省略可。中断時はworklogを作る |
| 通常 | worklog、仕様軸・標準軸のreview、必要な検証、完了報告を残す | retroゲートのトリガーを判定する |
| 大 | チケット単位のworklog/reviewと統合検証、完了報告を残す | セッション間のhandover、統合時の残存リスク、retroゲートを記録する |

条件に該当しない検査は「適用外」として理由を記録する。「適用外」は結果の値ではない。適用する検証の結果欄には、次の4値だけを使う。

小作業でも対象プロジェクトの既存テストは必須である。省略できるのは計画書、grilling、通常のworklogなどの工程であり、既存テストを省略して成功扱いにすることではない。実際のテストコマンド、実行場所、前提、期待条件はconfigから読む。

| 結果 | 記録する条件 |
| --- | --- |
| 成功 | 対象版に対して実行し、定めた期待条件を満たした |
| 失敗 | 実行したが、期待条件を満たさなかった |
| 未実行 | 実行していない。省略理由と、必要なら実行する条件を添える |
| 実行不能 | 環境・権限・依存などにより実行できない。代替確認と限界を添える |

「未実行」「実行不能」を成功へ読み替えない。修正後に再実行した場合は、前回の失敗・未実行・実行不能を消さず、再試行の結果を別行または同一識別子の履歴として残す。

## 2. 対象版を固定する

作業開始時に次をworklogへ記録する。

1. 作業場所、ブランチ、開始時刻、開始SHA。
2. 開始時点ですでに存在した未コミット変更と未追跡ファイル。今回の変更と混ぜない。
3. 検証時点のHEAD、未コミット変更、未追跡の対象ファイル、証拠の保存先。
4. 検証対象が複数ある場合の各対象版（パッケージ、環境、設定、データなど）。

HEADだけを対象版と呼ばない。作業ツリーに対象変更があるときは、その変更を含む状態を明示する。記録後に対象が変わった場合は、影響する検証を再実行するか、確認不能の限界を記録する。

## 3. reviewの範囲を作る

通常・大・高リスクの変更では、開始SHAを固定比較点として次の二軸を分けて確認する。

- **仕様軸**: 依頼、完了条件、対象チケット、`HARNESS_SPEC`相当の仕様に照らし、必要な結果が実装され、対象外を先取りしていないか確認する。
- **標準軸**: `AGENTS.md`、関連する規約、制約、既存テスト、配置・命名・リンク規則に照らし、リポジトリの標準に沿っているか確認する。

上流reviewがコミット済み差分だけを扱う場合も、未コミット変更と未追跡ファイルを除外しない。開始時の既存変更を別に示したうえで、開始SHAからの作業ツリー差分、`git ls-files --others --exclude-standard` で列挙した未追跡ファイルの本文、必要な生成物を二軸へ渡す。空のコミット差分をreview成功とみなさない。

review結果は、指摘、修正、残存リスクをworklogへ要約する。修正によって対象版や検証範囲が変わった場合は、影響する検証を再実行する。

## 4. 検証を実行して記録する

1. configから、変更した領域に必要な検証を選ぶ。必須検証、条件付き検証、適用外の理由を区別する。
2. configにある実行場所、コマンド、前提、期待条件を確認する。ローカルテスト、OKF検査、CI、独立smokeは別の識別子にする。
3. worklogの検証表へ、識別子、適用可否、結果、対象版・範囲、コマンドまたは確認方法、期待条件、証拠、理由・限界を記録する。
4. 失敗したら原因と修正を記録してから再実行する。再実行前の結果を成功に置き換えない。
5. 実行不能なら、試した方法、阻害要因、代替確認、確認できない範囲、再実行条件を記録する。

証拠は、終了状態と対象版を第三者が照合できる最小の参照にする。認証情報、会話全文、巨大なログをworklogへコピーしない。必要なら保存先と要約だけを残す。

## 5. 完了または中断を報告する

完了報告には次を含める。

- 成果: 依頼された結果と完了条件ごとの判定。
- 検証要約: 必須検証の識別子、4値、対象版、証拠。
- review要約: 仕様軸と標準軸の結果、修正した指摘、残存リスク。
- 未完了: 未実行・実行不能・失敗、未解決の判断、適用外の理由。
- full retrospective（retro）判定: トリガーの有無。トリガーありは [振り返り・改善台帳手順](retrospective.md) へ進み、根拠不足・実行不能・未処理の次の一手を記録する。トリガーなしは通常報告で終了する。

必須条件が満たせない場合は完了と報告せず、中断として [引継ぎ・再開手順](handover.md) に従う。中断報告には、具体的な次の一手、妨げ、再開前提、最新の検証状態を必ず残す。

## 6. retroゲートへ接続する

開始・再開時は、[プロジェクト設定](../../project/config.md)から [振り返り・改善台帳手順](retrospective.md) と `harness/ledger.md` の実配置を確認し、試行期限・採用済みの見直し日・期限切れ時の扱いを確認する。定時自動処理がない場合、無稼働中に期限確認が済んだとは仮定しない。

完了・中断時は、同手順に従って依頼・既決要件、対象差分、検証と再試行、review、引継ぎの記録を照合する。worklogには次の内容を残す。

- トリガーありなら、未処理の事象だけfull retrospectiveへ送り、更新した `IMP-NNNN` と判断待ちを参照する。
- トリガーなしなら、確認範囲と非該当理由を残して通常の完了・中断報告で終了し、空のretro文書や台帳行を作らない。
- 根拠不足、retroの実行不能、期限切れ処理の阻害、巻戻し競合があれば、摩擦なしやretro実施済みと断定せず、中断・確認不能の範囲と具体的な次の一手を残す。

full retrospectiveの詳細な分岐、台帳の重複・上限・試行・採否・撤去条件は [振り返り・改善台帳手順](retrospective.md) に置く。検証結果の4値、review、完了契約はこの手順のままとし、retroの有無で結果値を増やしたり成功へ読み替えたりしない。
